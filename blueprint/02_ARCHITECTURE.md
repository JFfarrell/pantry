# Architecture: Pantry

**Scope:** `blueprint/01_SCOPE.md`

## System Overview

Pantry is a single-user, offline-first Android application that closes the chain from *recipe found on the web* to *shopping done*, entirely on the user's own device. It is a single installable app with no backend, no accounts and no API keys: all user data (recipes, the shopping-list selection, shopping lists, retailer-assist progress) lives in a local Room database, and the only outbound network traffic is three user-initiated actions — fetching a recipe page (G1), looking up an ingredient's nutrition (G4), and loading the retailer's own site in a browser the user drives themselves (G5). A chosen recipe goes straight from the browse/compare view into the shopping-list selection and from there into a generated list, with nothing to designate in between (G2).

Structurally the app is one Gradle module organised as layered packages: a Compose UI layer over per-feature ViewModels, a domain layer of pure Kotlin engines (quantity normalisation, list merging, nutrition aggregation, seasonality evaluation), and a data layer split between mutable user data (Room) and read-only developer-curated reference data bundled in the APK. The pure-domain engines carry most of the project's correctness risk — unit merging, scaling, and the three-state seasonality rule — and are deliberately free of Android dependencies so they are unit-testable by a solo developer without a device. Retailer integration is intentionally the thinnest component in the system: a URL template plus a static section-ordering list, with every basket action left to the user on Tesco's own page.

## Components

### C1 — Recipe Import

- **Responsibility:** Turn a shared or pasted `http(s)` URL into an editable in-memory recipe draft.
- **Boundary:** Inside: intent/share-target handling, URL validation, triggering the fetch (the HTTP call itself is executed by C7, the app's sole HTTP call site), structured-data extraction (JSON-LD `Recipe`, then microdata/RDFa, then a heuristic fallback), image-source selection under the structured-metadata-before-inline-`<img>` preference order and triggering that image's fetch through C7 as a second, independent call sharing the same policy boundary as the page fetch, mapping to a draft model (carrying the validated in-memory image bytes for the draft screen to preview, or an explicit no-image state — the file itself does not exist until C3 writes it at persistence), and capture of `sourceUrl` + `fetchedAt`. Outside: the HTTP fetches themselves (C7), writing the fetched image bytes to storage and persistence generally (C3), ingredient parsing (C4), any judgement about whether the draft is *good* — that is the user's, via the editable draft screen (C9).
- **Key Concerns:** Untrusted remote HTML — parse defensively, cap *decompressed* response size (not the compressed transfer size, so a gzip decompression bomb can't bypass the cap) and redirect depth, bound JSON-LD parse/recursion depth, never execute page script, and reject non-`http(s)` or non-HTML input with a plain error rather than guessing (Non-Goals). Recipe pages are fetched using whichever scheme (`http` or `https`) the source URL specifies (Non-Goals require accepting both), with no certificate pinning even on an `https` fetch, so content is treated as untrusted regardless of transport — a network-level tamperer can only substitute different attacker-controlled HTML, which the same defensive-parsing posture already contains. Every failure mode (timeout, 404, unparseable page) must still yield a usable, editable draft or a clear error, never a hang or crash (G8). Import is the only network-dependent path into the catalogue and is explicitly out of the offline guarantee (G6). A candidate thumbnail image is exactly as untrusted as the page it came from: the fetched bytes are capped in size by C7 the same way page bytes are, and are decoded through the platform's image-decoding API and validated as a genuine raster image before the validated in-memory bytes are placed in the draft (not a file reference — no file exists yet) — bytes that fail to decode as an image are treated as "no usable image" (the same explicit no-image state a missing `<img>` produces), never retried as HTML and never passed through unvalidated. This validation decode is bounds-aware in exactly the same way C3's later downsample decode is (dimensions read first, a sample size computed, decoded at scale rather than at native resolution) — a malicious decompression-bomb-style image (small on the wire, enormous once decoded) is caught here, at C1, rather than assumed safe until it reaches C3's own bounds-aware step. The preference order Non-Goals names (structured metadata before a bare inline guess) resolves to a fixed three-tier lookup, evaluated in order and stopping at the first hit, independently of whichever tier the recipe's *content* extraction (JSON-LD → microdata → heuristic, above) landed on: a JSON-LD `Recipe.image` value; an `og:image` meta tag; the largest inline `<img>` by declared `width`×`height` (first-in-document as a tiebreak when neither declares a size). No hit at any tier means no usable image. No further extraction heuristic exists beyond these three tiers.

### C2 — Reference Data Store

- **Responsibility:** Serve the four bundled, developer-curated read-only datasets: the staples nutrition table (~170 raw ingredients), the canonical-ingredient alias table (Q2), the Republic of Ireland seasonality/substitution reference, and the fixed Tesco Ireland (`tesco.ie`) supermarket-section ordering list.
- **Boundary:** Inside: dataset files shipped in the APK, their schema, versioning, load-on-first-use and in-memory caching, lookup by canonical ingredient key, and the alias table's raw-text-variant → canonical-key exception mapping (Q2). Outside: the canonicalisation *logic* that applies the normalisation rule and consults that alias table (C4), any network-sourced data (C7), and any user-editable data (C3).
- **Key Concerns:** Read-only and immutable at runtime, so it is safe to share across components without locking. Must load without blocking first paint on a low-end device. Lookup misses are a normal, first-class result — "not in the table" is the signal that drives G4's unmatched-ingredient rule and G7's *unknown* state, so the API returns an explicit absence, never a zero or a default.

### C3 — Catalogue & Persistence

- **Responsibility:** Own the durable local store of user data and the CRUD operations over it.
- **Boundary:** Inside: the Room database, entities, DAOs, migrations, and reactive read streams (`Flow`) for recipes, shopping-list selection entries, shopping lists, and retailer-assist session state; the tap-delete/undo soft-delete mechanism — every recipe-backed `Flow` C3 exposes (to C9's catalogue and detail views, and to C5's selection reads) filters out any `Recipe` whose `pendingDeletionAt` is non-null, so setting that single column on tap-delete is what makes the recipe disappear immediately from every observer at once (catalogue, detail, and the selection with its G2 drop-notice), through the same reactive-`Flow` propagation every other edit already uses, with no separate cross-screen removal logic needed; clearing the column (Undo, within the window) makes it reappear with every field — including the thumbnail file reference — untouched, since nothing about the row was ever actually written during the pending window; writing a recipe's thumbnail — decoding, downsampling to a fixed maximum dimension and re-encoding as JPEG per Technology Choices — Thumbnail storage, for image bytes from either source (C1's already-security-validated import fetch or C9's device-photo-picker attach) — to a file in the app's private internal storage, recording that file's reference on the `Recipe` row, and deleting both the row and its thumbnail file together only at finalization (C9 calls through once its app-foreground-scoped undo-window timer elapses unopposed; see C9's Boundary) — never at the tap-to-delete moment, so an Undo within the window restores the thumbnail file along with everything else G1's undo guarantee names — or deleting just the file when a thumbnail is replaced, so no orphaned image file survives its recipe and no thumbnail is silently lost to an Undo; exposing a sweep operation — called by C9 at the same foreground-entry event that (re)creates its own timer scope, not run autonomously by C3 itself, since observing Android's lifecycle is C9's concern, not C3's — that unconditionally clears `pendingDeletionAt` on any row where it is still set from an interrupted prior foreground session (a cold launch or a resume from the background alike, not only the former), per G1's "the app process is killed **or** the app isn't returned to" discard requirement; a finalization interrupted by the app leaving the foreground for any reason, including but not limited to the process dying, is never resumed or completed silently, only ever discarded; this recovery sweep and C9's timer are two views of the same event (the app-foreground scope ending and, symmetrically, beginning again), never two independently-triggered mechanisms that could disagree about a row's state or leave a gap between them. Each recipe tracks its own pending deletion independently through its own row's `pendingDeletionAt` — there is one timer instance per pending deletion, not a single shared timer, so two recipes deleted moments apart each keep their own undo window and finalize (or get discarded) on their own schedule. Foreground-scoping is deliberately the *stricter* of the two readings SCOPE's criterion supports — a delete-then-immediately-return background blip discards the deletion just as a longer absence would, rather than trying to distinguish "brief" from "not returned to" — matching SCOPE's own stated preference for "the safer of the two possible outcomes." Outside: all business rules — merging, scaling, nutrition aggregation and seasonality evaluation live in C4–C6 and C10 and are never expressed as SQL; C1's untrusted-content security validation of network-fetched bytes (decode-as-image plus size cap, done before this point) or where the bytes came from; owning the undo-window timer itself (C9).
- **Key Concerns (thumbnail write path):** The decode-and-re-encode step is unconditional for every thumbnail regardless of source — it is what makes the storage-format decision (Technology Choices) actually true, not an optional pass. A source image that fails to decode here (a corrupted file, an unsupported format the platform decoder rejects) is treated the same way as C1's own decode failure — an explicit no-image state, never a write attempt on bad bytes and never a crash — so C9's photo-picker path, despite carrying no security-validation step of its own (picker-returned files are not adversarial), still gets this ordinary-failure handling for free by going through the same write path C1 uses. Decoding is bounds-aware — the decoder reads the source image's dimensions first and computes a sample size before decoding at scale, rather than fully decoding an arbitrary-resolution source (network-fetched or a full-resolution device photo alike) into memory at its native size — so a very large source image cannot exhaust memory before the downsample step ever runs. A local write failure (disk full, an I/O error writing to `filesDir`) degrades to the same explicit no-image state as a decode failure, never a hang or crash — the recipe itself still saves.
- **Key Concerns:** This is the whole of G6's durability promise: everything here must be readable with the network off and survive restarts and reboots. Referential integrity between a shopping-list selection entry and its recipe is load-bearing for G2's edit/delete-propagation criterion — selection reads observe the recipe, so an edit propagates and a delete surfaces as a dropped entry with a visible notice rather than stale data, while the servings figure the user set on that entry is their own choice for this shop and survives the edit rather than being re-copied from the recipe's yield. Schema migrations must be written from the first release, since a distributed app (G8) cannot assume a wipe-and-reinstall. Android's default app-data auto-backup is disabled for this database (see Technology Choices — Backup), so the OS itself cannot convey it off-device; without that control G6's "no Pantry data leaves the device" claim and Q1's "never conveyed" ODbL premise would both be false by default on a real device, not by app design. C3 bumps `Recipe.updatedAt` on every write to a `Recipe` row or one of its child `RecipeIngredient` rows — from C1's initial import or from C9's edit form (below) — since that field is the invalidation key R8's cache contingency and the Data Architecture section's reconciliation both name, and a nutrition/seasonality figure depends on the ingredient list, not only the parent row.

### C4 — Ingredient Normalisation & Quantity Engine

- **Responsibility:** Parse a free-text ingredient line into a canonical ingredient key plus a typed, dimensioned quantity, and decide when two quantities may be combined.
- **Boundary:** Inside: text parsing, the canonical-key normalisation rule (case-fold, strip preparation/quantity words, singularise) plus consulting C2's alias table for the exceptions that rule misses (Q2), unit modelling (mass / volume / count / unquantified), within-dimension conversion, scaling arithmetic, and the merge-compatibility predicate. Outside: curating or storing the alias data itself (C2), reading or writing storage, any cross-dimension conversion that would require a density estimate for the shopping list, and any nutrition or seasonality semantics — those components consume this component's keys and quantities rather than re-parsing text.
- **Key Concerns:** This is the correctness centre of G3. Combination is permitted only within one dimension and one canonical key (1 kg + 500 g → 1.5 kg), and never across dimensions or across distinct keys (400 g tomatoes vs. 2 tbsp tomato purée stay separate). An unparseable quantity yields an explicit *unquantified* value that propagates to the list, so no invented number can ever be produced. Pure Kotlin, no Android dependencies, exhaustively unit-tested — it is the cheapest place in the system to buy correctness.

### C5 — Shopping List Selection & Generation

- **Responsibility:** Maintain the set of recipes chosen for the next shop with their per-entry servings, and collapse that selection into one ordered, merged shopping list.
- **Boundary:** Inside: adding and removing a recipe to and from the selection, the per-entry servings figure and its default (the recipe's own stated yield, or a 1× baseline where the recipe states none), scaling each recipe's contributions by servings ÷ recipe yield, grouping by canonical key, merging via C4's compatibility predicate, assigning each entry a supermarket section from C2's ordering list, and emitting a stable walk-ordered sequence. Outside: quantity arithmetic itself (C4), section-list curation (C2), the nutrition and seasonality figures shown alongside a selected recipe (C6, C10), and how the finished list is worked in-store (C8).
- **Key Concerns:** A recipe enters the selection directly from a card or its detail screen with nothing to designate first, and goes from there to a generated list with no intervening step (G2) — there is no container between choosing a recipe and generating its list. Order stability — the same selection must produce the same sequence every time, with an explicit terminal bucket for entries whose section is unknown. Unquantified entries survive to the output marked as such. Both the selection and the generated list are persisted (C3) so each is fully usable with the network off (G6) and the selection survives restarts. A generated list is a snapshot as of the moment it was generated: a later edit or deletion of a source recipe changes the live selection (via C3's reactive reads), never an already-generated list (G2).

### C6 — Nutrition Service

- **Responsibility:** Produce per-recipe nutrition figures together with an explicit, honest provenance and confidence record.
- **Boundary:** Inside: resolving each ingredient against the staples table (C2) first and the external food-data source (C7) second, caching lookups locally, applying weight conversions, aggregating recipe totals, and computing the disclosure record — which figures rest on an estimated conversion and what proportion of ingredients contributed real data. Outside: any UI decision about how a caveat is rendered (C9), and any storage of user data beyond the lookup cache (C3).
- **Key Concerns:** G4's honesty rule is structural, not cosmetic: an unmatched ingredient contributes literally nothing to the totals and increments the unmatched count, and the aggregate is never emitted without its disclosure record attached. The component is usable offline against the staples table alone, degrading to a lower match proportion rather than failing (G6). Attribution and licence obligations for externally sourced figures are carried on the data as it is stored, so C9 can always render the required credit (G4).

### C7 — External Data Gateway

- **Responsibility:** Perform the app's data-fetching network calls — recipe page fetch, the recipe page's thumbnail image fetch, and ingredient nutrition lookup — behind one policy boundary.
- **Boundary:** Inside: the HTTP client, timeouts, retry/back-off policy, a transport-level cap on raw response bytes read off the wire (applied identically to a page fetch, an image fetch, and a nutrition lookup — the image fetch is not a special case), anonymous request construction — no keys, no credentials, no user data in any request beyond the recipe-fetch's or image-fetch's user-supplied/page-supplied URL (passed through as-is, since it is the GET target itself, not a query parameter) or the nutrition-lookup's ingredient term (URL-encoded via a URL-builder API before being placed into that request's query string) — and mapping every failure to a typed error. Outside: parsing page structure and enforcing the separate cap on decompressed-content size *as it streams during parsing* (not only checked after parsing completes, which would defeat a decompression-bomb defense) (C1), deciding an image's source URL or validating fetched image bytes decode as an image (C1), interpreting nutrition payloads (C6), and the retailer browser (C8) — which is not an HTTP client at all but a handoff to the system browser.
- **Key Concerns:** The single choke point for G6's "no Pantry data leaves the device" claim (for Pantry-initiated network calls; Room's own durable storage is covered separately by C3's auto-backup exclusion, since a backup isn't a call this gateway makes), which makes that claim auditable by inspecting one component. Every call must fail fast and visibly (G8): a timeout returns a typed error the UI renders as plain text, never a silent hang. Every connection target — the initial fetch and every redirect hop alike — is validated as `http(s)` before being connected to, so neither the original URL nor a redirect chain can hand a response off to an app-invoking scheme (`intent://`, `content://`); the resolved address of every such connection is also checked, on both address families, against loopback (`127.0.0.0/8`, `::1`), link-local (`169.254.0.0/16`, `fe80::/10`), and private ranges (RFC 1918 for IPv4, unique-local `fc00::/7` for IPv6) — so a URL shared from anywhere, whether it resolves directly or via a redirect chain, cannot make the device probe its own local network over either stack.

### C8 — Retailer Assist

- **Responsibility:** Walk the user through a finished shopping list one item at a time, landing each step on Tesco Ireland's (`tesco.ie`) own search results inside a browser the user drives.
- **Boundary:** Inside: a durable local queue pointer (position, skipped items), advance/skip/back operations, building the Tesco search URL from an item's text — URL-encoded via a URL-builder API, never raw string concatenation, since the text ultimately traces back to imported recipe content (C1) — and launching it in an Android Custom Tab. Outside: everything on the retailer's page — no DOM access, no injected script, no programmatic basket action, no navigation to checkout, and no retailer credentials (Non-Goals, G5).
- **Key Concerns:** The app's controls move a local pointer and nothing else; this is the property that makes G5's inspection criterion pass. Wording is part of the contract — progress text refers to the user's position in the local list and never asserts basket contents. The pointer is persisted (C3) so it survives backgrounding and process death. Custom Tabs is chosen specifically so the user sees the real domain and TLS state before any retailer login (G5, G8) — a bare `WebView` would fail that criterion.

### C9 — UI Shell & Accessibility Layer

- **Responsibility:** Render every screen, own navigation and app-level state, and carry the cross-cutting presentation obligations.
- **Boundary:** Inside: Compose screens, ViewModels, navigation, the first-run orientation flow, error surfaces, the caveat/seasonality indicator vocabulary, content descriptions, text-scaling support and contrast, and an edit form for an already-saved recipe (G2) — the same editable fields as C1's import draft, pre-populated from C3's stored row instead of a freshly-parsed draft, routing any edited ingredient line back through C4 the same way C1's draft confirmation does, and writing the result back through C3 on save; invoking the platform's device photo picker to attach or replace a recipe's thumbnail on manual entry or during that edit form, a local file selection with no network call of its own, handing the picked image's bytes to C3 to write and reference the same way an import-fetched image is written; the tap-delete undo affordance and its window timer — a coroutine scoped to the app's foreground presence as a whole (an app-level scope C9 owns, independent of any individual screen's own lifecycle, so in-app navigation between screens does not touch it), not a background job in the WorkManager sense, started the instant C3's `pendingDeletionAt` write returns and calling back through C3 to finalize (actually delete the row and its thumbnail) only if it runs to completion with no intervening Undo tap. Screen-level and process-level scoping were both tried and rejected in earlier design passes: a timer scoped to the deleting screen's own lifecycle is cancelled by the delete action's own forced navigation away from that screen (SCOPE fixes delete to the recipe's detail screen, and that screen's data source is exactly the row this action just made disappear via C3's `Flow` filter, above); a timer scoped to the process's lifetime survives backgrounding altogether, which lets a deletion finalize while the app was never returned to — a distinct discard trigger SCOPE's G1 criterion names ("the app process is killed **or** the app isn't returned to") and app-foreground scoping honours directly by construction. The remaining risk with foreground-scoping alone — a brief background/foreground cycle stranding the row if recovery only ran on a cold launch — is closed by making C3's recovery sweep (below) run on every entry to the foreground, not only a fresh process start: any interruption of the app-foreground scope, for any reason and for any duration, is treated identically to a kill for the purposes of this mechanism, and is always caught the moment the app is next brought forward — the same foreground-entry event that ends the previous scope (if one was still pending) also creates the fresh one this feature's timers run in, and calls C3's sweep, so recovery is never a step that could be forgotten or run late. Outside: all domain logic (C4–C6, C10) and all persistence (C3); ViewModels orchestrate and expose state, they do not compute merges or nutrition; C1's untrusted-content *security* validation (adversarial-content defenses — size caps against a hostile response, treating fetched bytes as attacker-controlled), which does not apply here since a file returned by the platform's own photo picker from the device's gallery is not adversarial network content the way a fetched image is. This is narrower than "no validation at all": C3's ordinary decode-failure handling (Key Concerns, below) still runs against picker-sourced bytes exactly as it does against C1's, since a legitimate device photo can still fail to decode for mundane reasons (corruption, an unsupported format).
- **Key Concerns:** G8 lives almost entirely here. Two visually distinct indicator families are required — seasonality state and nutrition caveat — each distinguishable by icon or text and not by colour alone, so a glancing comparison in the browse view cannot confuse them (G2, G8). The add-to-selection and remove-from-selection affordances are reachable from both the card/listing view and a recipe's own detail screen, and the per-entry servings control lives beside the selection entry itself (G2). Every screen must survive system font scaling without truncation, and every interactive element carries a content description. The nutrition-source attribution required by G4 has a permanent home here, alongside the in-app half of G8's privacy disclosure and best-effort-support statement (the store-listing half of each is authored outside the app, at Play Console submission).

### C10 — Seasonality & Substitution Service

- **Responsibility:** Report per-ingredient seasonality against the Irish (Republic of Ireland) growing calendar, supply substitutions for out-of-season ingredients, and compute a recipe's aggregate seasonality state.
- **Boundary:** Inside: lookup against C2's seasonality reference by canonical key, the current-date-to-season evaluation, substitution retrieval, and the three-state aggregate rule. Outside: dataset curation (C2), key derivation (C4), and how the states are rendered (C9).
- **Key Concerns:** The aggregate rule is evaluated in strict precedence and must not be reordered: **out of season** if any recognised ingredient is out of season, regardless of unknowns; otherwise **partial** if any ingredient is unrecognised; otherwise **in season** (G7). Unknown and out-of-season are distinct states and are never merged. An ingredient absent from the reference returns *unknown*, never a guess in either direction. Substitutions are always accompanied by the no-allergen-safety-guarantee disclaimer (G7, Non-Goals).

## Data Architecture

### Data Models (High-Level)

| Entity | Description | Owned By | Storage |
|--------|-------------|----------|---------|

| `NutritionSummary` | Per-recipe totals plus disclosure record: matched/total ingredient counts, estimated-conversion flags | C6 | Derived at read time, not stored |

| `SeasonalityEntry` | Canonical key → Irish (Republic of Ireland) months in season + substitution keys | C2 | Bundled JSON asset (read-only) |
| `SectionOrderEntry` | Canonical key → Tesco section; section → walk-order index | C2 | Bundled JSON asset (read-only) |

Derived entities (`NutritionSummary`, `SeasonalityState`) are deliberately not persisted by default: an *unkeyed* cache — one with no invalidation tied to the recipe it was derived from — would create a second source of truth that could go stale behind a recipe edit, which is exactly the failure G2's propagation criterion forbids. The default cost is recomputation on read, which is trivial at this data scale. R8 names a fallback if that assumption proves wrong under real measurement: a cache keyed and invalidated on the source recipe's `updatedAt` is not this failure mode, because a stale entry is provably detectable and never served — it is a performance contingency, not a reopening of the no-persistence default.

At rest, the Room database relies on Android's platform-level disk encryption — mandatory since Android 6.0 and, as file-based encryption specifically, universal by Android 10, so present on every `minSdk` 26+ device either way — rather than any additional app-level encryption. Treating a lost, shared, or rooted device as outside this document's threat model is this document's own architectural judgment call, not a SCOPE commitment: SCOPE names no device-loss or physical-access threat model one way or the other, and a single-user, no-accounts, personal-recipe app is judged here not to need a passphrase-gated store beyond what the platform already provides.

### Data Flow

The system has five flows, each terminating in local storage or in the user's hands. None of them sends Pantry-owned data outward.

```
IMPORT (G1) — the only inbound data path
  share/paste URL ─> C1 validate ─> C7 HTTP(S) GET ─> C1 extract (JSON-LD ─> microdata ─> heuristic)
       ─> C1 select image URL (preference order) ─> C7 HTTP(S) GET ─> C1 validate as image
              ─┬─ valid ─> draft carries the image
              └─ invalid/absent ─> draft carries explicit no-image state
       ─> editable draft (C9) ─> user corrects ─> C4 parse ingredient lines
       ─> C3 Room (Recipe + RecipeIngredient + sourceUrl/fetchedAt) + C3 decodes, downsamples and
              re-encodes the thumbnail as JPEG, writing the file (or no-image state if decode fails)
  any failure ──> typed error ──> plain message + still-editable empty draft

BROWSE & SELECT (G2)
  C3 recipes (Flow) ─> C9 browse/compare card
        ├─ C6 nutrition summary + caveat ──┐
        └─ C10 aggregate seasonality state ┤─> two distinct indicators (G8)
  add / remove ─> C5 selection entry (recipe ref, servings) ─> C3 Room
        (from the card or the detail screen; nothing to designate first)
  recipe edited ─> C3 Flow emits ─> entry updates
        (the servings the user set on that entry survives the edit)
  recipe tap-deleted ─> C3 sets pendingDeletionAt (row untouched otherwise) ─> C3 Flow emits
        ─> recipe disappears from catalogue/detail/selection at once, selection entry drops with a notice
        ├─ Undo tapped in window ─> C3 clears pendingDeletionAt ─> Flow emits ─> full reappearance
        ├─ C9's timer elapses unopposed while the app stays in the foreground the
        │     whole time ─> C3 deletes the row + thumbnail file (finalization)
        └─ app leaves the foreground before the timer completes (backgrounded, or the
              process dies — same handling either way) ─> timer ends, nothing resumed;
              C3's sweep on the next foreground entry clears the leftover
              pendingDeletionAt ─> recipe reappears

LIST (G3)
  selection {(recipe, servings)} ─> C5
        ─> C4 scale (servings / yield) ─> canonical key + dimensioned quantity
        ─> group by key ─> C4 merge-compatible? ─┬─ yes ─> combined entry
                                                 └─ no  ─> separate entries
        ─> unparseable quantity ─> entry marked UNQUANTIFIED (never a number)
        ─> C2 section lookup ─> walk-order sort (unknown section ─> terminal bucket)
        ─> C3 Room (ShoppingList + items)

SHOP (G5)
  C3 list ─> C8 queue ─> build Tesco search URL for item[i]
        ─> Custom Tab opens retailer's own page (user's own session)
        ─> user chooses product + quantity + basket action  [outside Pantry]
        ─> advance/skip/back moves the LOCAL pointer only ─> C3 Room (survives process death)

NUTRITION LOOKUP (G4) — the second and last outbound path
  canonical key ─> C2 staples table ─┬─ hit ─> value (offline, no network)
                                     └─ miss ─> C6 cache ─┬─ hit ─> cached value
                                                          └─ miss ─> C7 HTTPS (anonymous)
        ─> value + source attribution + licence tag ─> C3 cache
        ─> still unmatched ─> contributes NOTHING to totals; unmatched count +1
        ─> aggregate emitted only with its disclosure record attached
```

Three invariants hold across every flow. First, absence is represented explicitly — *unquantified*, *unmatched*, *unknown season*, *unknown section*, *unknown cooking time* — and never collapses into a zero, a default, or a silent omission; this single rule is what makes G3, G4 and G7's honesty criteria enforceable rather than aspirational. Second, no flow carries Pantry-owned data outward: the import request contains only the URL the user supplied, the nutrition request contains only an ingredient term, and the retailer flow hands a URL to the system browser and receives nothing back. Third, no exception constructed anywhere in Pantry's own code embeds raw user-supplied or imported content — a recipe URL, an ingredient line, a fragment of fetched HTML — in its own message, whether that exception is caught and converted to one of the typed-error surfaces named in each component's Key Concerns, or left to propagate as an unhandled crash. This reaches every component that touches such content on its way through the system (not only the ones named elsewhere for a specific concern, such as C1's parsing or C7's network calls, but also, for example, C8's retailer-search text or C3's persistence layer). Where a third-party library's own exception (e.g. OkHttp's, jsoup's) might itself embed such content in its message, the component that calls that library re-wraps it into one of the typed-error surfaces before it can reach a caller unchanged, rather than letting the library's exception propagate as-is. Failures are reported through a category and a plain message, never the offending payload. This is what makes the External Dependencies section's claim that Android vitals crash/ANR reporting "never carries recipe, selection, or shopping-list content" actually true — covering both a handled failure and an unhandled crash — rather than an assumption about a platform behaviour Pantry's own code doesn't control.

No dependency in this table is load-bearing for the app's core offline function. Every one of them can be unavailable while browsing recipes, choosing them for a shop, and generating and reading a shopping list continues to work (G6).

Android vitals is Play Services' own platform-level crash/ANR instrumentation, present for every Play-distributed app regardless of what network calls its own code makes. It carries only stack traces, ANR timing, and bounded device metadata (OS version, device model, app version — never an advertising or install identifier), and never recipe, selection, or shopping-list content: that property is made true by the Data Flow section's third invariant above (no exception constructed in Pantry's own code, caught or uncaught, embeds raw user-supplied or imported content, and third-party library exceptions are re-wrapped before they can propagate unchanged), not assumed as an inherent platform guarantee. Nor is it conveyed to a Pantry-operated destination — it goes to Google, which operates Play itself. G6's Success Criteria have two clauses: an unconditional one ("No recipe, selection or shopping-list data is transmitted anywhere," satisfied by the same invariant) and one scoped to a *Pantry-operated* destination "because none exists" (satisfied because vitals goes to Google, not Pantry). Read most literally, G6's "the only outbound network activity is [three named actions]" sentence still doesn't name vitals as a fourth item; this document resolves that by scoping the enumeration to Pantry's own application-level network activity — code the developer writes and controls — treating Play Services' automatic, always-present instrumentation as platform-level in the same sense that OS-level traffic (time sync, connectivity checks, Play Store's own update checks) isn't attributed to whichever app happens to be installed. That scoping is this document's own resolution, not a textual amendment to SCOPE; if a future revision of SCOPE wants to speak to platform-level traffic explicitly, that is a SCOPE-phase change, not an Architecture one. For a low-install-volume solo-developer app, expect vitals data to be sparse in the early weeks after each release (also noted in the table row's Risk/Fallback columns above) — treat it as a supplement to the developer's own pre-release device testing (G8), not a substitute for it, until install volume is large enough for vitals dashboards to populate meaningfully.

## Open Questions

> All questions must be resolved before proceeding to the next phase.

- [x] Q1: Does Open Food Facts' ODbL licence, as actually written, impose any obligation beyond visible attribution given that the app stores ODbL-derived values in a device-local cache that is never redistributed — and does the bundled staples table need to be provably independent of that data to stay outside the share-alike scope?
  - **Resolution:** Resolved — attribution only; no share-alike obligation attaches. ODbL's share-alike and Derivative-Database provisions are triggered by *Publicly Conveying* the Database or a Derivative Database to third parties; using query results (an ingredient's nutrition record, fetched one term at a time) to produce a *Produced Work* — the per-recipe nutrition summary shown to the same user who made the request — falls under ODbL's Produced Work provision, which requires only an attribution notice, not share-alike, and specifically does not require re-licensing the underlying data. Independently, a cache that is never conveyed to any third party (stays on the requesting user's own device, is never exported, published, or shared) is not "Publicly Conveyed" under ODbL at all, so even if the accumulated per-recipe lookups were construed as a Derivative Database, ODbL's obligations do not engage absent public conveyance. Both readings converge on the same outcome: the architecture's design (R3) — visible attribution in C9, and a device-local, licence-tagged cache kept structurally separate from the bundled staples table (C2) and excluded from Android's own auto-backup (Technology Choices — Backup) so it is never conveyed even incidentally by the OS — satisfies the licence as written. The bundled staples table (C2) is developer-curated from scratch and never derived from Open Food Facts content, so it needs no independent-provenance argument; C6's structural separation of the two datasets (staples in C2, ODbL-sourced lookups in C3's cache) keeps this true by construction rather than by policy.
- [x] Q2: Is the canonical ingredient key derived by rule (normalise, strip preparation words, singularise) with an explicit alias table for exceptions, or by an exhaustive curated alias list alone?
  - **Resolution:** Resolved — rule-derived with an explicit alias table for exceptions. A pure normalisation rule (case-fold, strip preparation/quantity words, singularise) handles the regular case cheaply and predictably; the alias table in C2 carries only the exceptions the rule gets wrong (irregular plurals, brand-name-to-generic mappings, regional spelling variants), keeping C2's curation burden proportional to actual exceptions rather than to the full ingredient vocabulary. This is already the shape R6's mitigation commits to ("Aliases are explicit data in C2, not inferred by fuzzy matching") — this resolution makes explicit that the rule supplies the default and the table supplies the override, rather than the table being exhaustive.
- [x] Q3: Which recipe fields must the extraction layer produce for a draft to count as usable — is cooking time required (G2's browse/compare view depends on it) or optional with a user-supplied fallback?
  - **Resolution:** Resolved — optional at extraction, rendered as an explicit unknown, never blocking. SCOPE's G1 success criteria commit that "no import path ends in a state where the user's only option is to abandon it," which rules out forcing manual entry of a missing field before a draft can be saved. Cooking time therefore follows the same explicit-absence pattern already used for unquantified ingredients (G3) and unknown seasonality (G7): C1 stores it when the source page provides it and leaves it absent otherwise (never a guessed default); C9's browse/compare view renders an explicit "unknown" indicator for a recipe missing it, consistent with how C9 renders C6's nutrition caveats; the draft screen (C9) lets the user fill it in at any time, same as any other field.
